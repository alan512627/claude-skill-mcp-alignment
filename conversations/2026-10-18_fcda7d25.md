**Tool knowledge**

For this person's remote device workflow, firmware test result archives are delivered as nested zip files: an outer zip (e.g., OVL3_Castle_Peak_Firmware_Cycles_*.zip) containing per-slot "*_Complete" zip files, which themselves need extraction to reach the actual log directories (e.g., stos_downgrade/). The working approach was to mkdir a working directory under $HOME, unzip the outer archive, then loop over all inner *.zip files extracting each to a same-named subdirectory before searching logs. Log files from this pipeline mix two formats: SOC-side logs (e.g., 0XX_*.log files) use a `Success : True` field, while RM (Rack Manager)-side logs (e.g., 014_rm_dc_cycle.log) use `Result : SUCCESS` / `Completion Code: Success` instead — both must be checked when verifying a given step, since grepping only for `Success : True` would miss RM-side confirmations. Log content often contains literal `\n` escape sequences rather than real newlines, which should be preserved as-is when quoting raw log excerpts to the person. ANSI color codes (`\x1b[[0-9;]*m`) are commonly embedded in these logs and should be stripped via sed before display. The compliance summary file is named consolidated_compliance_check.txt and sits alongside the numbered step logs in each stos_downgrade directory per slot.
