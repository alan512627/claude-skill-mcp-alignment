**Tool knowledge**

For ADO Work Items API (`_apis/wit/workitems`), `$expand=relations` and `fields=` parameters cannot be used together in the same request — this throws a `ConflictingParametersException` (HTTP 400); when relations are needed, omit `fields` entirely since `$expand` returns all fields anyway. For ADO Test Plan Suites API (`_apis/testplan/Plans/{planId}/suites/{suiteId}`), PATCH requests require the current `revision` number to match, and `queryString` values are normalized by ADO on save (e.g., `OR` becomes lowercase `or`), so read-back comparisons must be case/whitespace-insensitive to avoid false "mismatch" errors. Rejected PATCH writes (e.g., malformed WIQL) return HTTP 400 with `InvalidPropertyException` in the response body — this is distinct from HTTP 401/403 auth failures and should not be treated as a permissions issue. When parsing numeric IDs out of WIQL `queryString` text, quoted string literals (like Area Paths containing version numbers) must be masked out first to avoid false-positive ID matches. For multi-ID WIQL clauses pulling Test Cases via linked Requirements, `[Source].[System.Id] IN (a, b)` in this ADO instance only returns cases from the first listed ID — the reliable syntax for pulling cases from multiple Requirements is `([Source].[System.Id] = a OR [Source].[System.Id] = b)`, matching the ADO query editor's "ID = a / Or ID = b" grouped rows, wrapped in parentheses to avoid breaking other AND conditions in the query.
