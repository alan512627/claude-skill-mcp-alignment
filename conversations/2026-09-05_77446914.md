# Rack management controller timeout optimization

- Date: 2026-09-05

## Summary

The person is working on a test rack infrastructure and sought Claude's help diagnosing and resolving SSH connection and timeout issues affecting their Rack Management Control Board setup. The technical environment involves two Rack Management Control Boards (each with only 2 CPU cores) acting as intermediaries between a VM server running Ansible-based test scripts and 22 SUT (System Under Test) nodes per board. Each board maintains 22 simultaneous SSH connections to SUT management controllers, with a constraint of one SSH connection per SUT. The core problem is that when test scripts execute and send commands concurrently, the 2-core Rack Management board cannot handle the volume of simultaneous SSH operations, resulting in frequent timeouts.

Claude provided a structured diagnostic and solution framework. The diagnostic approach emphasized identifying whether the root cause is OpenSSH's `MaxStartups` limit dropping connections (default `10:30:100` would reject connections beyond 10 simultaneous unauthenticated sessions), CPU saturation from SSH key exchange cryptographic operations on the 2-core chip, or Ansible repeatedly re-establishing SSH connections without ControlPersist. Claude provided specific commands to check `sshd -T` settings and `vmstat` output during script execution.

On the Ansible configuration side, Claude provided a complete `ansible.cfg` configuration recommending `forks` set between 4–8 (with empirical sweep testing), enabling `pipelining = True`, configuring `ControlPersist=600s` to reuse SSH connections, setting `gathering = explicit` to skip costly fact gathering, and selecting optimal SSH ciphers (`aes128-gcm` with hardware AES or `chacha20-poly1305` without it) based on ARM chip capabilities. For architectural solutions, Claude ranked options by implementation cost: TCP port forwarding on the Rack Management board to offload SSH encryption to endpoints (most recommended), a bounded worker queue with Ansible async mode to prevent concurrent request storms, pre-establishing persistent SSH connection pools, migrating from SSH to Redfish/IPMI for BMC communication, and splitting the 22-node load across the two existing boards (potentially the fastest win). Claude explicitly cautioned against simply increasing timeout values as a first step, as this masks rather than resolves the underlying concurrency bottleneck.
